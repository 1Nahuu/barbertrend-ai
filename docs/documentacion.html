1. Resumen ejecutivo

BarberTrend AI es una aplicación web para una barbería masculina que combina dos módulos: un sistema de reservas online y, más adelante, un asistente de marketing con IA para detectar tendencias y generar contenido para redes.

Hoy el primero de esos módulos ya está operativo de punta a punta:

  • La web pública muestra los servicios, precios, horarios, galería y contacto con datos reales de la barbería.
  • Un cliente puede reservar un turno de verdad. La disponibilidad la calcula el backend y el sistema garantiza que dos personas no puedan quedarse con el mismo horario.
  • El barbero entra a un panel privado, ve los turnos y los puede confirmar, completar o cancelar.
  • Cuando entra un turno nuevo, el barbero recibe un aviso por email en forma automática.
  • Al confirmar, el panel le da un enlace de WhatsApp con el mensaje ya escrito para avisarle al cliente: se envía con un toque, sin costo y sin depender de la API de Meta.

El sistema es 100 % gratuito en su operación actual: no usa servicios pagos, y el único requisito para recibir emails es una cuenta de Gmail con contraseña de aplicación (también gratuita).

2. El producto

El proyecto se pensó como un producto útil para un negocio real (una barbería familiar) y, a la vez, como proyecto de portfolio reutilizable para otras barberías. La estrategia fue construir por etapas, sin incorporar tecnologías nuevas hasta que hicieran falta.

2.1 Sistema de reservas

  • Web pública responsive con catálogo de servicios y precios.
  • Selección de fecha y horario, con disponibilidad calculada en el servidor.
  • Reserva de turnos con datos básicos del cliente.
  • Garantía de que no se superpongan dos turnos.
  • Consulta del estado de un turno mediante un código.
  • Panel administrativo privado para gestionar la agenda.
  • Avisos al barbero y al cliente.

2.2 Asistente de marketing (etapa posterior)

  • Detección de tendencias del rubro a partir de fuentes verificables.
  • Ideas y guiones breves para Reels e historias.
  • Captions y hashtags; recomendaciones periódicas.
  • Historial de sugerencias y registro de resultados.
Regla de oro del proyecto: la IA debe generar contenido a partir de información disponible y verificable. No se inventan tendencias, estadísticas, enlaces ni métricas. Cada dato se distingue entre verificado, estimado, sugerencia creativa o no obtenido.

El sitio y el panel son archivos estáticos servidos por la misma aplicación. Esto simplifica el despliegue (un solo servicio) y evita problemas de CORS. Cuando haga falta, se puede separar sin reescribir nada, porque el frontend sólo habla con la API por HTTP.

8. La garantía anti-superposición de turnos

Esta es la parte más importante del sistema y la que justifica varias decisiones de diseño. Como es un negocio real, dos personas reservando el mismo horario a la vez es exactamente lo que va a pasar.

8.1 El problema del enfoque obvio

El código "pregunto si está libre y, si está, lo grabo" tiene una condición de carrera: entre la consulta y el guardado entra la otra petición, que también ve el horario libre, y las dos graban.

8.2 La solución: bloques ocupados

La jornada se divide en bloques de 30 minutos. Una reserva no ocupa un instante: ocupa bloques. Un corte de 60 minutos a las 10:00 inserta dos filas: (barbero, 10:00) y (barbero, 10:30).

La tabla appointment_slot tiene clave primaria compuesta (barber_id, slot_start). Cuando alguien intenta tomar un bloque ya ocupado, el INSERT viola esa clave y la base de datos rechaza la operación. La aplicación traduce ese rechazo a 409 Conflict.

Por qué no alcanza con un UNIQUE(barber_id, starts_at): dos turnos pueden empezar en instantes distintos y pisarse igual. 

10:00 → 11:00   y   10:30 → 11:30
Los dos starts_at son distintos, pero las dos personas quedan en la misma silla.

Ocupar bloques hace que el conflicto se vea siempre, sin importar cómo se combinen las duraciones.

8.3 El bug que apareció en las pruebas

La primera versión usaba saveAndFlush(...). Las pruebas de concurrencia fallaban: en lugar de una sola reserva exitosa, quedaban muchas. La causa:

  • Con una clave compuesta asignada a mano, Spring Data no ve la entidad como "nueva" (la clave no es nula), así que usa merge.
  • El merge primero consulta; si otro hilo ya insertó el bloque, actualiza la fila existente en lugar de fallar.
  • Resultado: el que perdía la carrera se quedaba con el bloque del ganador.

La corrección fue implementar Persistable y marcar la entidad como nueva. Así Spring Data usa persist y el INSERT choca con la clave primaria. Las pruebas de concurrencia (20 peticiones simultáneas al mismo horario) pasan.

EstadoSignificado¿Ocupa el horario?
PENDINGReserva recibida, esperando confirmaciónSí
CONFIRMEDConfirmada por el barberoSí
COMPLETEDEl servicio se prestóYa no
CANCELLEDCancelada, con motivoNo (libera el horario)
Un turno PENDING sí bloquea el horario. Si dos personas piden las 10:00, la segunda recibe 409 aunque la primera todavía no se haya confirmado. Sin esa protección, ambos turnos entrarían a la lista de pendientes.

El código de referencia

Cada turno recibe un código corto y aleatorio (BT-7K2M9Q). Sirve para que el cliente consulte su turno sin iniciar sesión y sin ver los datos de otros. No es secuencial, porque eso permitiría adivinarlos.

  • Distinguir explícitamente datos verificados, estimaciones y sugerencias creativas.

Etapa 6 — Fuentes de tendencias Pendiente

Hallazgo importante. La API oficial de Instagram no ofrece búsqueda de hashtags ni de tendencias: sólo da insights de las publicaciones propias, publicación de contenido, moderación de comentarios, menciones y mensajería. Por lo tanto, el asistente no puede sacar tendencias de Instagram por API oficial. Habrá que usar fuentes reales y verificables (por ejemplo, YouTube Data API, que permite búsqueda con cupos, o feeds RSS del rubro), documentando fuente por fuente permisos, límites y costos antes de escribir código.

Etapa 7 — Automatización Pendiente

  • Búsquedas programadas en la zona horaria de Argentina.
  • Generación automática de recomendaciones y resumen por WhatsApp.
  • Evitar ejecuciones simultáneas; reintentos controlados.
  • Registros de actividad y opción de pausar.

Etapa 8 — Seguimiento y métricas Pendiente

  • Registrar qué ideas se usaron y cuándo se publicaron.
  • Cargar métricas manualmente y relacionarlas con turnos.
  • Comparar formatos y orientar las próximas recomendaciones.

No se afirmará que una publicación generó una reserva si no hay una forma razonable de relacionarlas.

Etapa 9 — Despliegue Pendiente

  • Comparar proveedores de alojamiento y estimar costos mensuales.
  • Configurar variables de entorno y base de datos persistentes.
  • Publicar la web con HTTPS.
  • Probar reservas reales controladas y verificar persistencia.
  • Documentar mantenimiento y recuperación ante errores.
Mejoras cercanas al sistema de reservas (antes o junto con la Etapa 4): extender un turno desde el panel cuando un corte se pasa de hora, y avisar de los horarios que quedaron apretados al día siguiente.

Cierre

BarberTrend AI tiene hoy un sistema de reservas completo y en uso: el cliente reserva, el barbero administra su agenda desde el teléfono y recibe un aviso automático por cada turno nuevo. Todo esto funciona sin costo operativo.

Lo que sigue apunta a reducir trabajo manual (automatizar el WhatsApp y los recordatorios), a llevar el sistema a internet de forma segura y, en paralelo o después, a sumar el asistente de marketing con IA sobre fuentes de datos verificables.
